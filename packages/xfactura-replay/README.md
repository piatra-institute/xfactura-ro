# Replay workspace

This private package inventories a corpus, provides an accountant's journal treatment for private replay engines, compares filed books and returns, and tracks differences in an append-only private store. Inventory and comparison never post or approve accounting records. Core XML parsing and the engine's PDF attachment adapter are reused; the engine and core are unchanged.

Run `bun scripts/differential/inventory.ts <source> <output> --dry` to print counts without creating the output. Without `--dry`, nonexcluded files are copied with their relative paths and all records are written to `<output>/manifest.json`. Add `--repair` only to explicitly permit replacing different output bytes; `--dry` still writes nothing when combined with `--repair`. Real corpora and their manifests belong in the root's ignored `.private/corpus/`; never commit real inputs or derived records. Files with identical content form a group whose owner is the path with the fewest segments, then the first in code-unit order, and every other member has `duplicateOf` pointing at that owner. A copy whose existing manifest names an owner chosen by another rule is refused, even with `--repair`, because repair never deletes files: remove the output folder and copy again. Run `bun run test:replay` for synthetic fixtures.

## Account and partner mapping

Run `bun scripts/differential/mapping.ts <company-alias> <D406 files or folders> [--saga <dump folder>] [--out <file under .private>]`. The default output is `.private/mapping/<company-alias>.json`; it is read before proposing additions, so reruns keep decisions and confirmations. The CLI uses `readD406`, the engine's reference chart plus amendments, and an empty existing-party list for offline proposals. It creates no engine accounts, parties, items or entries. An engine caller supplies the complete `accounts.list` and `parties.list` results to `proposeMapping(filed, chart, parties, previous?, { source?, saga? })`; account-list pagination belongs to the caller.

When `.private/corpus/manifest.json` exists, the input files identify the company and the manifest selects all its D406 filings by normalized fiscal code and form, across every folder and period. `duplicateOf` chains resolve to the copied canonical file; missing owners, cycles, excluded owners, unsafe paths, symlinks and changed file hashes block selection. PDF attachments use the existing engine adapter. XML payload hashes collapse identical re-filings, including the same XML filed inside a PDF; different payloads in one period remain. `periodsCovered` counts distinct Header selection intervals and `filedDocuments` counts distinct XML payloads. Corpus inputs without their manifest are refused. `readCompanyFilingDocuments(fiscalCode, manifestPath?)` makes the same selection for a fiscal code and returns each payload with its bytes and SHA-256. Standalone inputs outside the corpus remain usable without a manifest, with byte-identical files collapsed.

`src/mapping/schema.ts` owns the strict Zod schema for `schemaVersion: 1`; `src/mapping/mapping.schema.json` is generated with `bun packages/xfactura-replay/src/mapping/generate-schema.ts`. Instances belong only under `.private/`. A document's `company` is its normalized Header registration number and `source` names its account namespace (`d406` unless supplied); another company or explicit source cannot reuse it. Accounts retain the exact source ID and dotted standard ID, control kind, target code/name, synthetic or analytic kind, and analytic create/existing action. Partners use `{ origin, role, id }` so equal customer/supplier program codes do not conflate identities. Every source entry and placeholder records `decidedBy` and `confirmedByPerson`; the proposer never sets the latter true or assigns `person`.

The proposer first retains prior mapped, person-owned or confirmed entries. It retries only unresolved, unconfirmed rule entries. It then maps partners by country-scoped normalized fiscal code (`partner-fiscal-match`, `partner-fiscal-create`), or creates them with a source-scoped key when SAF-T explicitly declares no fiscal code (`partner-source-id`); names never establish identity. The SAF-T identity prefixes are decoded separately from the underlying fiscal code, including RegistrationNumber values that repeat CustomerID/SupplierID. A shared fiscal creation key denotes one party across source IDs and roles. Conflicting identities, countries, ambiguous matches and missing facts remain `unresolved` with a fixed reason code.

Account rules require the exact standard synthetic to be postable in the supplied chart. `account-synthetic` uses it directly, including off-balance synthetics; `account-analytic` preserves the full dotted standard code on an uncontrolled account, creating an analytic only if it is absent. Existing analytics use their engine name. New analytics require a general-book parent because that is what `accounts.create` supports; other books yield `ACCOUNT_ANALYTIC_UNSUPPORTED`. A nested analytic also needs its immediate parent in the supplied chart. Integer IDs are never split by guessing a synthetic prefix. When the standard is absent, a unique exact SAGA CONT spelling or its dot-free AccountID can supply it. Unknown, invalid, nonpostable or conflicting standards remain unresolved.

Controlled accounts always target the synthetic and carry a partner binding. `control-line-party` uses explicit line identities, or transaction identities inherited only when the line supplies neither a real identity nor a no-counterparty marker. All uses must identify one decided party before this rule applies. Otherwise `control-master-party` uses exact customer/supplier AccountID links, and `control-saga-party` uses an exact SAGA ANALITIC link when the D406 lacks it. Explicit identities take precedence across roles and over account fallbacks; a customer's identity can belong to an associate's payable. Conflicting identities block, including when a person confirmed an account binding or retained a line-role hint. Two source roles that map to the same engine party are one decided identity. Open-item controls require an item when replayed; the `tax` kind on VAT accounts requires tax entries or settlement instead, as the existing kernel does.

SAGA parsing checks the declared columns and row counts of CONTURI, CLIENTI and FURNIZORI and trims padding. Before C_SAFT can reuse a D406 party, the row's COD_FISCAL and identity must agree with that party. A conflicting link becomes a separate unresolved SAGA source entry with `PARTNER_IDENTITY_CONFLICT`; it cannot route the account to an otherwise valid D406 mapping or fall through to a placeholder. Program partner codes remain opaque when C_SAFT is absent. The dump supplements the filed account namespace; unrelated unused dump accounts and partners are not added.

`control-placeholder` declares one clearly marked artificial party per company and source account when the source supplies no counterpart. Its neutral label and null fiscal code make no claim about a real identity; its bookkeeping kind is `ro_individual` for employee controls and `ro_legal_entity` otherwise. These placeholders are separate from source partners and require a person's confirmation before `checkMapping` clears them. SAGA's own-company identifier is decoded as a no-counterparty marker before journal and payment references are collected; it is never a source party or an inherited counterparty on a marker-only line. Optional journal/payment `0` references also mean absence, while `0` on a required invoice identity blocks as `SOURCE_ID_MISSING`. Several possible master-file partners without complete line identities are ambiguous and stay unresolved.

To record a person's choice, edit the target in the private JSON, set `decidedBy: "person"` and `confirmedByPerson: true`. A person may also confirm a rule's unchanged decision by setting only its confirmation flag. Such confirmations concern mapping decisions only; they never approve a posting proposal. Rule decisions do not otherwise require confirmation; unresolved entries, unconfirmed person decisions and unconfirmed placeholders block. Previous entries stay in their original order and new entries append, so indexed review paths remain stable. Source account/control changes detected on a later check block despite retention of the earlier target.

`checkMapping(mapping, filed)` covers every master account/partner and all journal, invoice and payment references, plus stock-movement lines and asset references. It returns fixed problem codes and property/index paths for unresolved or missing mappings, duplicates, incompatible control kinds sharing a target, invalid control analytics, dangling partner/placeholder bindings, contradictory creation keys and missing/ambiguous line partners. The mapping schema validates shapes; `checkMapping` must also pass before replay, and the engine must still validate account availability at the posting date. Neither function posts or computes monetary values.

The CLI writes proposals even when blocked, then exits 2; unreadable inputs, malformed previous mappings or invalid arguments exit 1; a clear check exits 0. Its JSON summary contains source account/partner counts, source entries by rule, unresolved entries by reason with indexed paths, placeholder counts per indexed account, and blocking codes/paths. Placeholder declarations are counted separately from source entries. It prints no source names, identifiers, filenames or amounts, including parser errors. Writes must remain lexically under the worktree's `.private`, whose shared root may be a symlink; nested/file symlinks are rejected. Atomic mode-0600 replacement protects existing hardlinks, and unchanged JSON is not rewritten.

Existing party-operation limits stay explicit: a SAF-T 05 EU non-VAT entity has no corresponding engine party kind (`PARTNER_KIND_UNSUPPORTED`), and CNPs returned by `parties.list` are keyed or masked rather than comparable fiscal codes (`PARTNER_FISCAL_CODE_OPAQUE` when such existing individuals prevent ruling out a match). A SAF-T 09 NIF or another Romanian individual's identifier that fails the engine's CNP check cannot become a creation (`PARTNER_PARTIES_CREATE_REQUIRES_CNP`). These require a person's decision; mapping never relabels an EU non-VAT entity as taxable, guesses that an opaque individual is new, or proposes an individual the operation would refuse. Missing historical synthetics remain chart gaps rather than invented accounts. No engine/core or database change is part of this workspace.

The manifest is an array sorted by relative path using code-unit ordering. Each record has its byte size, SHA-256, kind, return XML metadata, duplicate owner, exclusion reasons and problem codes. The path with the fewest segments, then the first in code-unit order, owns its hash, validator files included; duplicates and validator files are excluded. Exclusion reason counts overlap when a duplicate is also a validator file. Summary counts include excluded records; form/version and company counts count each distinct value once per file.

XML namespaces identify forms and versions, including D112's `declaratie_unica` namespace. Fiscal codes and period values retain their XML spelling; missing fields and absent or unrecognized rectification flags are `null`. No filename supplies fiscal metadata. An attached return is called a signed return PDF only when the adapter detects a signature dictionary; this does not verify a signature. Annual statement PDFs require attached statement XML. Other readable PDFs use metadata and then directory/name clues for receipts and e-Factura renderings. SQLite signatures in folders containing `revisal` identify labour-register exports; archive signatures under database folders take precedence over validator-kit directory names. A `.pdf` extension cannot override those signatures. Unrecognized files remain `other`.

PDF attachments are read asynchronously through the engine's isolated adapter (`pdfAttachments`), which cross-checks `pdf.js` against `pdf-lib` across document embedded files (including those inside object streams) and page `/FileAttachment` annotations; inventory runs unique file inspection with bounded concurrency (4 readers at once) and retries unsettled reader failures (`timeout`, `failed`) once. An XFA form's internal `EmbeddedFile` stream alone is not an attachment. When the adapter reports `ambiguous`, a reader timeout or failure, or fails/finds nothing while PDF structure inspection still sees file specifications or an embedded-files name tree, the record carries `PDF_ATTACHMENTS_AMBIGUOUS`, `PDF_ATTACHMENTS_READER_FAILED`, `PDF_ATTACHMENTS_IN_OBJECT_STREAM` or `PDF_ATTACHMENTS_UNREADABLE`, and an unreadable PDF carries `PDF_UNREADABLE`.

The namespace-aware streaming reader projects only identity attributes into `sourceXml`, including the employer or old D394 identification child when needed. This avoids the core reader's attribute limit on historical return roots. For D406, `sourceXml` reads the actual bounded Header fragment; company tax registration, selection dates and HeaderComment supply its classification. Reading stops at that header; hashing still reads every byte. This inventory does not validate the remaining XML or read amounts. Archives are never extracted. Failed PDF/XML reads are recorded without copying exception text into the manifest.

Source symlinks are rejected. Copy preflight rejects traversal, reserved manifest paths, overlapping trees and existing symlinks within the output. Existing files or a manifest with different bytes raise `OUTPUT_CONFLICT: <relative path>` before any copy writes. Explicit `copyCorpus(source, output, records, { repair: true })` or CLI `--repair` allows replacement, including changes to an existing manifest as the inventory changes, but an output whose owners follow another rule is refused even with `--repair`. Replacements use temporary files inside the output and verify their hashes. Unchanged files and an unchanged manifest are not rewritten. Copying does not prune files left by earlier inventories, and source changes after inventory fail the copy instead of silently changing the recorded bytes.

## Accountant's journal replay

`src/treatments/journal.ts` exports `migrationJournal`, its strict `migrationJournalInput` schema and `MigrationJournalInput` type. Inject the treatment with `new Engine(db, objects, secret, { treatments: [migrationJournal] })` in a private replay engine. It is not registered in the product and has `agent: false`; neither its typed operations nor the generic proposal operation allow an agent to propose it. Replay still uses `migration.journal.propose`, a person's approval of the exact effect hash, and `ledger.post`; it provides no direct write path and reads no rule parameters.

The input names a colon-free `source`, the source transaction's stable `reference`, retained source-file `evidenceId`, `date`, `journalCode` and `description`. The subject is `migration:<source>:<reference>`. Repeating identical input returns the existing proposal, including after posting; changed input for that subject is refused with `SUBJECT_EXISTS`. This is the kernel's normal recognition semantics: withdrawal or reversal can free the subject for a corrected proposal.

Each line supplies `account`, `side` and a signed decimal `amount` in RON; optional `currency` supplies `code`, signed decimal `amount`, `rateId` and `rate`. Optional `analytics` contains `costCenter`, `project` and `item`; `memo` is also preserved. A control line names either an existing `openItem` UUID or a `newItem` ref declared in `newItems`, never both. New declarations provide `ref`, `partyId`, optional `dueDate`, optional `documentId` and optional `mayReverse` (false unless supplied); their account, kind, normal side and currency follow their lines and the chart, as in `ledger.general`.

Each supplied tax entry names `key`, `tax`, semantic `code`, `direction`, signed decimal `base`, `amount`, `deductible` and `booked`, `taxPoint`, nullable `exigibility`, nullable `taxPeriod`, and `attributes`. Optional `line` is a zero-based line index; an entry without a line must book zero, as checked by the kernel. Optional `partyId`, `documentId` and `originTaxEntry` are preserved. Optional `currency` supplies `code`, `baseMinor` and `taxMinor` as signed integer strings in that currency's minor units, `rate` and `rateId`; the minor-unit strings become exact integers without scaling, and the other fields pass through unchanged. Amounts are parsed exactly, without computing tax, conversion, totals or rounding. Reverse charge supplies input and output tax entries in one transaction. VAT on collection supplies a deferred entry on 4428 and later signed release entries on 4428 and 4426 or 4427; releases may omit `documentId`.

Period-closing lines on 4426/4427 carry `taxSettlement: { tax: 'VAT', period: '<period>' }` instead of tax entries. The 4423/4424 counterpart is an ordinary open-item control line. The treatment reports unknown evidence, partners, documents and existing items, undeclared or unused new items, new items on accounts without open items, and tax entries naming non-tax lines. `validateEffect` blocks a VAT line without tax entries or a settlement marker (`TAX_LINE_UNEXPLAINED`) and a control line without an item (`CONTROL_OPEN_ITEM`); the acceptance tests confirm the treatment itself emits neither finding and approval is refused before database posting. The unchanged database remains the posting backstop.

### Limits

The input cannot express stock quantities/layers/moves, stock transfers without journal lines, or schedules. It emits general `effect@1` entries only. Retail price-method postings still need their warehouse analytics and the existing kernel rules; replay does not bypass them. Unsupported currencies, amounts finer than their minor unit, and amounts outside the bounded decimal input format are refused without rounding. None of the requested synthetic accountant entry shapes required a database guard change.

A tax entry can reference only the tax-controlled line it books, not the expense, revenue or other base line that generated its tax base. The treatment also carries no dedicated withholding or allocation details for the D406 writer. Both gaps belong to the task that rebuilds returns from the imported journal; replay does not infer those links or details.

A source control line without a partner must be resolved to a party by the mapping, as must any missing itemization; replay does not invent a partner or item. A line may omit `partyId` when its declared or existing open item already identifies the party.

## Return comparison

Run `bun scripts/differential/compare-return.ts <engine.xml> <filed.xml>` for a JSON summary with counts by class and top-level XML section, and keyed paths. Root attributes belong to `$root`. Add `--values` to include the differences and their original values; that output belongs in the private workspace. Set `XFACTURA_REPLAY_HASH_KEY` to a caller-managed secret for stable personal-key pseudonyms across runs. Without it, the CLI supplies a fresh random secret for each invocation. The secret is never printed or stored.

`src/compare/returns.ts` exports `compareReturns(engine, filed, catalogue)`, `catalogueFor(declaration)`, `returnCatalogues`, `inspectReturnKeys(declaration, catalogue)` and `summarize(differences, key)`. The inputs are core's `FiledDeclaration` objects. Different forms, namespace versions or reporting periods are refused. The two D112 layouts additionally select by reporting half-year; S1005 v15 is restricted to financial year 2025. The other catalogues select by namespace version, including historical files sharing that namespace; comparison is not schema or tax validation. Missing periods, missing required keys, duplicate keys within a parent and repeated elements without catalogue keys are errors. Errors do not quote row identifiers or input values.

Repeated elements receive their key even when they occur only once and the reader omits `[1]`. Each key component is percent-escaped; `~` denotes an absent optional component, distinct from an empty string. Descendant keys are scoped to their parent. A missing repeated subtree produces one `structure` difference whose present-side value is a map of its nonignored fields, without duplicate differences for its descendants. A missing scalar keeps `null` on the absent side and remains a difference. When the catalogue marks the field numeric and its present value is exactly zero, the class is `zero-omission`; it has no delta and is counted separately by `summarize`. Other one-sided scalars, including nonzero numeric values, are `text`. No absent field is equated to zero. Unknown scalar fields remain visible. Numeric comparison applies only to catalogued numeric fields, so numeric-looking identifiers stay text. Numerically equal decimal spellings produce no difference; unequal amounts carry an exact signed decimal `delta` (engine minus filed). Malformed numeric strings are text differences.

All shipped tolerances are zero. The writers serialize already-rounded amounts; their deterministic rounding rules and validators' formula slack do not authorize a nonzero difference between returns. The `rounding` class supports explicitly supplied exact-decimal tolerances and is tested at and beyond its boundary using a synthetic catalogue. No comparison computes tax, totals or rounded return amounts.

Cosmetic policies are scoped to the listed name, address and declarant fields in `catalogues.ts`: surrounding spaces, letter case and diacritics; company/partner names also allow a terminal legal-form suffix. These differences are reported as `cosmetic`, not discarded. No policy changes identifiers or broadly removes punctuation or internal spaces. Partners without a code use their supplied name (and D394 address) as identity. Name key components allow trimming, letter case and diacritics only: legal-form suffixes remain part of identity, so an uncoded SRL and SA are distinct rows. Display-name fields on coded rows can still use legal-form normalization. Normalization collisions are refused rather than matched by position.

Every catalogue ignores root `@{http://www.w3.org/2001/XMLSchema-instance}schemaLocation`: this is a producer's schema-location hint, while the namespace version is checked separately. Catalogue entries also conditionally ignore whitespace-only `#text` on each known attribute/element-only element, with the reason stated beside the entry; non-whitespace text and unknown elements remain visible. The other unconditional ignores and every repeated-element key are listed below; `?` means an optional attribute. No software-name or generation-date field is assumed or ignored without an explicit entry.

`summarize` requires a nonempty caller key and emits no values, deltas or subtree payloads. It applies domain-separated HMAC-SHA-256 to D112/D205 personal identifiers, medical-certificate identities, uncoded partners' identifying names/addresses, all D394 type 2 `cuiP` keys (individuals or unregistered entities), and any key component whose trimmed value is 13 digits (including a D394 CNP/NIF). Nonpersonal business keys remain in paths. Use a secret of sufficient entropy; do not publish it with a report.

The comparator inherits `readDeclaration`'s projection limits: an element with no attributes, text or descendants contributes no field, so its presence cannot be detected (for example an empty annual F40); element namespaces are reduced to local names. Empty-element inventory or element-namespace distinctions would require a core reader change, outside this package. Whitespace-only text on catalogued attribute/element-only elements is ignored as indentation; text elsewhere remains visible. Optional omitted cells remain absent and are not silently equated to explicit zero cells.

`bun run test:replay` exercises actual writer output from synthetic core test inputs, reorderings of every catalogued repeated path, single/multiple transitions, independent mutations of every key component and key variant, nested additions/removals, amount/text mutations with path and value assertions, zero omissions, exact arithmetic and tolerance boundaries, normalization restrictions, refusals, summary privacy and CLI output. D300 and S1005 have no repeated paths to remove or add; their tests reorder their actual layout and mutate fields without inventing a repeating row schema. Corpus checks are read-only and must use counts and schema paths in reports, with no private fixtures or extracted values added to this package.

## Payroll source readers

Run `bun scripts/differential/payroll-sources.ts <corpus> <output> --key-file <path>` to read the manifest's included `.rvs` labour-register exports and standalone D112 XMLs whose reporting year is 2026. Excluded duplicates and embedded PDF attachments are not read again. Output must be below a directory named `.private`, including after resolving that directory's location; symlinks below it cannot redirect output. The command verifies selected source sizes and SHA-256 hashes and parses every source before writing anything. It creates a missing 32-byte random key with mode `0600`; an existing key must be a regular, owner-only 32-byte file with no additional hard links. The key and output paths must be separate: neither may contain the other, and the key must be outside the corpus. Keep that key for comparable subsequent runs. Output JSON files have mode `0600`, the output directory `0700`, and filenames use source hashes rather than personal source filenames. Reruns replace these files without pruning older outputs; a fresh output directory preserves earlier projections when the model changes.

`readRevisal(bytes, key)` checks a single regular `.xml.pcs` tar member, including the tar checksum, paths, sizes and trailer, and passes its ZIP bytes to the engine's bounded archive adapter. It requires one `XmlReport` XML in the Revisal namespace throughout. Decimal spelling is preserved, absent terms and currency stay `null`, and export time is explicitly identified as the tar member's UTC modification timestamp, not an XML effective date. The contract state is the state encoded in that snapshot; a contractual end date and an actual termination date remain separate. `changes` carries salary and working-time observations dated by `DataConsemnare`, explicit suspension/termination dates, and structured preceding states where present, in date order with undated observations last. A snapshot does not establish previous salary/time terms or a complete change history. `allowances` reads `SporuriSalariu/Spor`: its type, type version, percentage flag and original decimal value; `typeKey` is a separately domain-separated HMAC of `Tip/Nume`, allowing comparison of employer-defined allowance labels without retaining free text. An absent or nil allowance container remains `null`; an explicitly empty container is an empty list. Nil `StarePrecedenta` is consumed. Uninterpreted audit entries, free text, names and other unused leaves are counted in `unread` without retaining their values; unsupported attributes are counted separately. Empty and nil unused leaves also count, while namespace declarations and nil-control attributes do not.

`readD112Employees(declaration, key)` accepts core's `FiledDeclaration`. The `d112FieldNames` table derives numeric fields and neutral names from the engine's 2026 v7 writer and ANAF's 2026 structure, including employee sections A, B1–B4, D, E1–E3, and employer A, B, C1–C4, D, E1–E3, F1 and F2. Each figure keeps its field name, section, one-based section occurrence and original decimal string. Missing figures are never filled or totals recomputed. A table entry of `null` carries a known numeric writer field without inventing a meaning. Coverage separates `numericFieldsWithoutNeutralName` from `fieldsOutsideMappingTable`; `unmappedFields` includes both. Unknown fields contribute paths without copying their values. Older or otherwise unsupported layouts retain period/employer metadata and hashed insured identities but no guessed figures, and list their unplaced sections. A 2026 return must state a valid reporting month; missing and invalid months have explicit error codes. This is a projection, not XSD or tax validation; `FiledDeclaration` does not retain descendant element namespaces, so this reader cannot separately validate those namespaces. Names, contacts, certificate numbers, diagnoses and other people's personal codes are excluded.

Each employee's `classifications` retains known contract/working-time codes, norm hours, insured type, pensioner and insurance flags, minimum-contribution exception and reason, income-tax exemption, contribution-payment flags, medical-leave category and E3 section/job/period classifications. `d112ClassificationFields` specifies their neutral names and bounded code syntax. They are separate from `figures`, preserve their source spelling and are never converted into tax treatment decisions. `employerClassifications` carries the contribution-liability and obligation codes, plus `F2_cif` and `F2_id` to identify each secondary establishment's figures by the same section occurrence. Employer D and E1–E3 summarize categories declared through insured section C; their neutral names distinguish them from employment-contract totals. F1 and each F2 retain income tax owed, payable, deductible and exempt as four separate source figures.

The neutral names were reviewed against the writer and ANAF's [January–June 2026 structure](https://static.anaf.ro/static/10/Anaf/Declaratii_R/AplicatiiDec/structura_D112_0126_300326.pdf) and [July–December 2026 structure](https://static.anaf.ro/static/10/Anaf/Declaratii_R/AplicatiiDec/structura_D112_0726_070926.pdf): employer C1–C4 on pages 13–23, D/E on pages 24–30 and F on page 31; employee A on pages 36–41, B on pages 42–51, D on pages 56–62 and E on pages 63–74 of the July structure. `A_sal2` (field 14b) and `B1_sal2` (29b) describe gross contract pay. Accounting programs often leave them at zero when the corresponding base-salary field is supplied; that recorded zero is preserved. Both readers use the same domain-separated HMAC-SHA-256 of the trimmed personal code and a caller-supplied key of at least 32 bytes. No raw personal code, name or secret is returned. The script writes individual neutral models and a count-only `summary.json`, also printed on stdout: export timestamps and contract observation counts, returns and insured counts by month, distinct insured-person matches against any supplied register snapshot, aggregated unread paths and uncovered D112 fields/sections. `coverage.json` lists every encountered field outside the mapping tables, every numeric field still without a neutral name, and every unplaced section, with counts. Real sources, neutral models, key files and source-derived reports belong under `.private/` and must never be committed. Synthetic archive, privacy, layout, writer round-trip and output-containment tests run with `bun run test:replay`.

## Book comparison and difference tracking

`src/compare/balances.ts` exports `compareBalances(source, engine, mapping)`. Supply a complete `D406Filed[]`, an `EngineBalancePeriod[]`, and `(sourceAccount: string) => engineAccount | undefined`. The result contains rows with both sides' opening debit/credit, debit turnover, credit turnover and closing debit/credit, plus one difference per unequal or unknown field and source-chain findings. Amounts are canonical exact decimal strings, using the same arithmetic as return comparison; `delta` is engine minus source and is absent for unknown values. Source turnover sums the supplied general-ledger lines. Many source accounts mapping to one engine account combine their turnover by side and their opening/closing balances by net side. An undefined mapping produces a `mapping-account` finding; missing accounts and reporting intervals are separate presence findings, including an explicitly present zero account. The option `{ zeroPresence: 'separate' }` (or `separateZeroPresence(differences)`) turns a one-sided account whose present side is zero throughout into `balance-presence-zero`, and a one-sided source-chain account whose stated balance is zero into `source-chain-presence-zero`: SAGA lists an account only in periods where it has a balance or movement, so these are counted apart from balance differences; without the option every caller keeps the earlier kinds.

D406 balance fields form a debit/credit choice: one stated valid side establishes zero on its absent opposite side. An opening or closing stated on both sides produces a `source-balance-both-sides` finding for the raw source account before mapping or aggregation, including when either side is zero or the net matches the engine. Both absent, or invalid amounts, remain unknown. Source balance comparison requires the declared ledger currency to be RON. A full calendar month's period is `YYYY-MM`; another complete selection interval is `YYYY-MM-DD/YYYY-MM-DD`. Duplicate or overlapping source selections, duplicate account IDs, mixed company identities and separate multi-segment declarations are refused. The caller must select the intended filed revision and supply complete declarations, rather than expecting the comparator to choose or assemble them.

`src/compare/engine.ts` exports `readEngineBalances(read, financialYearId, from, to)` and `readEngineJournals(read, from, to, limit?)`, where `read<T>(operation, input): Promise<T>` invokes operations as a person who can read the private books. The balance adapter uses `ledger.trialBalance`; its annual opening is used at the financial-year boundary, otherwise the engine's preceding closing supplies the period opening. No engine balance is recalculated by the adapter. The journal adapter exhausts `ledger.journal` pagination and reads `proposals.get` with `recheck: false` for the posted subject and tax entries, checking the entry binding. An optional fifth argument, `taxView(entry)`, states how each posted tax entry is compared (code, base, tax, deductible, period) or leaves it out with `null`; by default each is compared under its own code. Redacted reads and nonadvancing cursors are refused. No database read or write bypasses operations.

`src/compare/journals.ts` exports `compareJournals(sourceTransactions, engineEntries, mapping)`. Each source item supplies the exact `source` and `reference` used by `migration.journal`, a `D406FiledTransaction`, and optional evidence-backed `taxEntries`. `transactionsFromD406(filed, source, referenceBuilder)` flattens journals without guessing the replay's reference scheme. Subjects are matched exactly as `migration:<source>:<reference>`; colons inside the reference are preserved. Reused subjects on either side are an error. Each paired transaction compares the merged multiset of account, side and exact amount, retaining explicitly present zero groups and signed corrections. One `journal-lines` finding contains the two merged lists; moving a line produces one finding with both affected accounts. An incomplete mapping produces mapping findings and still compares all mapped source lines against the engine lines, retaining every other line and tax difference in that transaction. Engine groups without a mapped source counterpart remain visible in that comparison. Accounting-period changes and unpaired transactions on either side are separate findings.

Taxes compare as multisets of code, base, tax, deductible and period, preserving duplicate entries and ignoring ordering. Codes are compared literally; this comparator does not translate an ANAF code into an engine semantic code. Filed D406 taxes always establish the rows, their code, base and amount, including missing fields. Supplemental `taxEntries` add only deductible amount and VAT period; an empty supplement cannot remove filed taxes or introduce new rows. Each supplement names optional zero-based `filed: { line, tax }` coordinates; without those coordinates its array position refers to the corresponding tax in filed line/tax order. Explicit coordinates allow sparse or reordered supplements. Any supplied code/base/tax is an assertion checked against the filed facts, using exact decimal equality for amounts. A conflicting assertion, duplicate target or nonexistent target produces `source-tax-supplement`; the contradicted supplement cannot establish deductible or period. That source finding is retained for unpaired transactions too.

An undefined tax field is missing evidence; an explicit null period means not yet exigible. Known fields are compared using multiset matching and an unknown field always generates `journal-tax-evidence`, even if all known fields match. A changed filed code or other known field still generates `journal-tax` alongside any evidence or supplement finding. No missing tax fact becomes zero or an inferred period.

In a `source-tax-supplement` finding, `source` carries filed facts and `engine` carries supplemental evidence. Other valid supplements still augment their own filed rows. Missing filed code/base/amount remains unknown even when a supplement asserts a value.

`src/compare/source-chain.ts` exports `checkSourceChain(filedPeriods)`, independently of the engine and mapping. It sorts by selection dates, compares each raw account ID's stated closing sides with its next opening sides, and returns private `findings` and counts. On chain findings, `source` is the previous closing and `engine` is the next source opening; the delta is next opening minus previous closing. Renumbering remains visible as `source-chain-only-previous` and `source-chain-only-next`. Missing balance evidence and noncontiguous intervals have their own kinds. `transitionsChecked` counts contiguous period pairs; `accountsCompared` counts account identities present in both members of those pairs, including pairs with missing balance evidence. Accounts present on only one side are findings but are not counted as compared.

Run `bun packages/xfactura-replay/src/compare/source-chain-cli.ts --manifest .private/corpus/manifest.json <fiscal-code>...` for the read-only counts check across every manifest path belonging to each company. It selects return metadata by fiscal code and form D406, follows `duplicateOf` to the stored owner even in another folder tree, verifies file hashes and actual declaration identity, and reads only the selected XML or PDF attachments. It rejects broken or circular duplicate references and unsafe paths. Programmatic callers use `sourceChainCounts(manifestPath, fiscalCode)`. Fiscal codes are input only; counts-only output contains no codes, paths, amounts or findings. Results follow the order of the requested companies.

The runner collapses identical declaration bytes and equivalent re-filings of one period. Equivalence for this source-chain check requires the same raw account IDs and exact opening/closing sides, preserving missing and dual-side declarations; generation metadata, account ordering and decimal spelling do not change those facts. A changed account set or balance for the same period is `SOURCE_CHAIN_PERIOD_CONFLICT`; other overlapping selections are refused. This checks equivalence of chain inputs, not journals or the rest of the return. `declarations` counts retained periods, `filesRead` counts unique stored files read, and `duplicates` counts decoded byte duplicates or equivalent re-filings discarded, excluding manifest aliases that resolve to a file already selected. The directory-only invocation `bun packages/xfactura-replay/src/compare/source-chain-cli.ts .private/corpus/<alias>/406` remains available for a deliberately restricted folder check and cannot establish complete company coverage when files live elsewhere. The runner writes no derived records, replays no entries, and runs no other D406 consistency checks. Parse failures print only a safe error code. This is not ANAF validator verification.

### Private event store

Every comparator finding starts as `unclassified` and `open`. Its SHA-256 ID includes a version tag, kind, period and sorted structural locator only: never the compared values, delta, tax code being compared or classification. Full findings and raw account/reference locators are private data. `src/compare/store.ts` exports `DifferenceStore(privateRoot, companyAlias, area?)` for `.private/<companyAlias>/differences.jsonl`, or `.private/<area>/<companyAlias>/differences.jsonl` with an area. It rejects traversal and area/company/file symlinks, creates private directories/files, and writes only append operations. `read()` folds the log into the latest values, class and status for every ID, including resolved findings. An observation may carry a `context` outside its identity: the lab assumptions it rests on, the reason codes of its driver's translation decisions (`notes`), the refusal of its source transaction, and a `cause` (class and reason code) its driver knows.

Call `reconcile(scope, completeDifferences, causes?)` with the full result of one comparison scope. Reappearing IDs retain their classifications while their observations are appended with the current values. IDs absent from that scope's new result receive appended resolution events. Reappearing resolved IDs reopen and keep their classification. Use distinct scopes for balances, journals and deliberately partial period ranges; a journal-only rerun must not resolve balance findings. Reusing an ID across scopes is refused. `classify(id, class, { id: personId, reason })` appends a person's decision referring to that ID. Rule classifications append their cause ID. A finding still unclassified after the repository causes takes its observation's `context.cause`, appended as a `replay` classification with its reason; like a rule, it never replaces a person's or a rule's class. A per-company lock rejects concurrent access; a truncated or malformed log fails closed without repair or rewriting. After an interrupted writer, a person must inspect the log and stale lock before retrying.

The classes are `engine-defect`, `accountant-choice`, `legal-reading`, `unsupported`, `missing-evidence`, `mapping`, `comparator`, `source-inconsistency` and `unclassified`. `legal-reading` records work for the expert; classification never approves a proposal or raises a rule's review status. The store does not classify on an agent's behalf or invent decisions.

### Public causes and shareable counts

`causes/<id>.json` contains an `id`, English `explanation`, `class`, structural `pattern` and, for `engine-defect`, a `fixture` path under `test/fixtures/` that reproduces it synthetically. A pattern requires `kind` and optionally names `accountSynthetic`, an inclusive monthly `period: { from, to }` range, and `taxCode`. It has no value, amount, transaction reference or company selector. `loadCauses()` validates each repository file, filename identity and referenced fixture. `applyCauses(differences, causes)` and store reconciliation apply rules only to open unclassified findings. Multiple matching causes are refused rather than resolved by ordering. The shipped source-balance-carry cause identifies a source inconsistency; it does not invent the accountant's explanation.

Cause validation rejects personal-code shapes, IBANs including spaced forms, prefixed or labelled company codes, unlabelled five-to-ten-digit integer codes, and numeric amounts with more than two significant digits. It scans whole numeric tokens, including mixed dot/comma grouping and decimal separators; trailing decimal zeroes do not add significance. Only the strictly validated pattern fields for synthetic accounts, period bounds and tax codes are exempt from amount/code scanning where their numeric shape is structural; personal-code, explicit company-code and IBAN checks apply there too. Unknown JSON fields are rejected. Names cannot be detected reliably by shape: the guard cannot establish that prose is anonymous, so causes must remain structural and every explanation and fixture needs human review for real names or other identifying context. Tests scan every shipped cause and exercise each forbidden shape using invented examples; synthetic fixtures remain subject to the repository's no-real-data rule.

`src/compare/differences.ts` exports `summarizeDifferences(differences, key)`. It counts open findings by class, kind, period and synthetic account, with no values, deltas, IDs, subjects or analytical suffixes. Each finding counts once per affected synthetic account; an unrecognized source account gets a caller-keyed HMAC pseudonym. Supply a nonempty caller-managed key and reuse it privately for stable pseudonyms. Resolved findings do not enter these counts. `gate` is true exactly when no open finding remains unclassified; it says nothing about whether a classified defect has been fixed.

## Filed journal replay

Run `bun scripts/differential/journal.ts <company-alias> [--from YYYY-MM] [--to YYYY-MM] [--lab-assumptions <file under .private>]`. It reads `.private/mapping/<alias>.json`, selects the mapping company's D406 payloads with `readCompanyFilingDocuments`, deletes and recreates `.private/replay/<alias>/engine/`, replays every kept period through `migration.journal` and writes `summary.json` and `manifest.json` (mode 0600) beside the engine. Differences go to `DifferenceStore(.private, alias, 'replay')`, that is `.private/replay/<alias>/differences.jsonl`; the engine secret stays in `.private/replay/<alias>/engine.key` so that reruns seal alike. Stdout repeats the summary. The exit code is 0 for a completed run, 2 for a run the mapping blocks and 1 for an error, printed as a code only; `XFACTURA_REPLAY_DEBUG=1` adds the stack, which may quote source values, for local use.

`src/run/driver.ts` exports `selectPeriods(filings, { from?, to? })` and `replayCompany(input)`. One filing is kept per selection interval: re-filings that state the same books (selection, currency, accounts, partners, journals and source documents) collapse to the latest created, then the greatest payload hash; re-filings with different books stop the run (`PERIOD_REFILINGS_DIFFER`). `--from` and `--to` keep the intervals inside those months. The first kept interval must start a financial year (`FIRST_PERIOD_NOT_YEAR_START`), and every filing must declare RON.

`src/run/assumptions.ts` owns `labAssumptionsSchema` (`schemaVersion: 1`, optional `company` that must equal the mapping's, `statedBy`, `accept` and `accounts`). `accept` names proposed entries accepted as they stand: an account by `sourceId`, a partner by `source`, a placeholder by `sourceAccountId`. `accounts` maps an unresolved `sourceId` to a `target` in the mapping's account shape, with the `party` binding a control account needs. Each entry may carry a `reason`. `applyLabAssumptions(mapping, filed, assumptions?)` applies them to a copy only: the mapping file and its `confirmedByPerson` flags are never written. It refuses an entry the mapping does not hold (`ASSUMPTION_ENTRY_UNKNOWN`), an acceptance of an unresolved entry, a target for an entry that is not unresolved, two assumptions about one entry and another company. An acceptance waives only its entry's `PLACEHOLDER_UNCONFIRMED` or `PERSON_DECISION_UNCONFIRMED`; every other `checkMapping` problem blocks the run before the engine opens, and the summary lists the blockers by code. Each assumption is named by its path in the file (`accept.0`, `accounts.2`); the manifest lists those applied and how many transactions used each, and every difference they touch carries them in `context.assumptions`.

`openReplayEngine(directory, { secret, seed, clock })` opens a new database with `migration.journal` injected, an empty rule register, a fixed clock (noon UTC on the day after the last kept interval) and identifiers seeded from the alias. One person owns the company, so segregation of duties is off: they propose, approve each version's exact effect hash, acknowledging its warnings (counted in the summary), and post. The same inputs give the same accounting records and the same summary; `created_at` columns, the command log and the audit chain keep wall time.

The company takes the first header's CUI (without RO) and name, and its first financial year; later years are created when reached. Mapped analytics are created with `accounts.create`, valid from the first interval's start, and the mapping's parties and placeholders with `parties.create`. Each kept filing is recorded once as evidence (`d406-<start>-<end>.xml`) and cited by every transaction posted from it.

The opening posts the first interval's master-file opening balances on its first day; books that open with nothing post no opening entry. A control account's balance opens one item per partner and account when the partners' own openings add up to it, otherwise one item of the partner or placeholder the mapping binds the account to; without either, the opening is refused (`OPENING_PARTY_UNKNOWN`). Accounts stating no opening are counted, never opened at zero. Off-balance and management accounts (books other than `general`) are single entries that no balanced entry carries: they are left out and listed (`outsideDoubleEntry`), and their balance differences are classified `unsupported`. The driver tries `ledger.general` with purpose `opening` first. That treatment records no tax entries, so a 4426, 4427 or 4428 balance is refused (`TAX_LINE_UNEXPLAINED`); the whole opening is then posted through `migration.journal` with journal code `DESCHIDERE`, each VAT-account line explained by one tax entry coded `CARRIED`. That entry books the filed balance with a zero base and tax: input VAT on a debit, output VAT on a credit, not exigible on 4428, and in no VAT period of these books. The summary names the treatment that took the opening, the general journal's refusal and the VAT accounts carried. `CARRIED` is no code D406 knows: `declarations.prepare` for a D406 cannot run on a lab database holding such an entry, and the VAT registers and returns, which read entries by VAT period, leave it out.

`src/run/translate.ts` turns one filed transaction into one `migration.journal` input, purely. Its reference is `<interval start>/<JournalID>/<TransactionID>`, its date the GLPostingDate (the TransactionDate when absent) and its tax point the TransactionDate; amounts, currencies and rates are the filed ones (`rateId: d406`) and its journal code the JournalID. A control line's party is the line's own partner (the transaction's when the line names neither a partner nor the absence of one), then the account's binding to a source partner, then its placeholder. An invoice that names the transaction as its posting opens one item per party, account and currency for its lines, known by the invoice number (also kept in the line memo); it may cross sides only if it opens on the wrong one, as a credit note does. An invoice whose key (account, party, number, currency) already names an item still opens its own: the key becomes ambiguous, neither item is found by it again, and the reuse is stored as a `replay-invoice-key-reused` difference (`source-inconsistency`, `INVOICE_KEY_REUSED`). A payment line matched by account, amount and partner, or the line's own SourceDocumentID, names the document whose item a line settles (counted as `settledByDocument`). Any other line uses the party's unallocated item, one per party, account and currency, which also carries the opening and may cross sides. A partner's settlement whose document has no open item is noted as `SETTLEMENT_NO_DOCUMENT`, `SETTLEMENT_DOCUMENT_AMBIGUOUS` (the document's key is reused: `source-inconsistency`), `SETTLEMENT_DOCUMENT_UNFILED` (no filed invoice of that partner has the number), `SETTLEMENT_DOCUMENT_ELSEWHERE` (that partner's invoice is on another account: `source-inconsistency`), `SETTLEMENT_BEFORE_INVOICE` (its invoice is replayed later), `SETTLEMENT_INVOICE_REFUSED` (`unsupported`) or `SETTLEMENT_ITEM_NOT_OPEN`, each stored as a `replay-settlement-unallocated` difference. A placeholder party's lines (taxes, payroll) name no invoices and keep their unallocated item without a note.

`src/run/taxes.ts` reads SAGA's TaxInformation blocks by role. TaxType 000 without an amount marks a line without tax relevance. TaxCode 380200 marks a VAT closing note, whose 4426 and 4427 lines carry `taxSettlement` for the transaction's month. A block with a zero amount and no base marks the line it sits on: SAGA repeats an operation's code on its 4426, 4427 and 4428 lines and marks a deduction's reversal, a cash-VAT release, an import's VAT or an exempt purchase this way. Other VAT blocks are operations; other taxes with an amount or a base have no place in `migration.journal`. Each operation and each marker on a VAT line is read with `d406CodeReadings`: a code without a reading is refused (`TAX_CODE_UNREAD`), and a code with several is kept only where the line's VAT account, or the transaction's VAT accounts, leaves one (`TAX_CODE_AMBIGUOUS` otherwise). No code in `d406AmbiguousTaxCodes` today has readings that differ in direction or VAT on collection, so each one with a base is refused; the tests show the account resolving an invented ambiguous code. A marker of an import's code (`IMP-*`) off the VAT accounts, as SAGA puts 301201 on a customs agent's 462 line, books the transaction's VAT line of its direction when exactly one such line carries no code (`IMPORT_MARKER_ATTACHED` in the transaction's notes and the entry's `attachedLine` attribute); any other marker off the VAT accounts posts nothing. A marker off the VAT accounts whose code a return reports (a reading with a D300 row, such as 308302 or 301201) stays in the comparison: it states no base, the engine holds none, and the `journal-tax` difference is classified `missing-evidence` (`MARKER_WITHOUT_BASE`); no base is made up from the line's amount.

An operation books the VAT line of its direction (4428 under VAT on collection): the line SAGA marks with its code first, then an unmarked line, several lines matched to several operations by exact amounts; a non-deductible operation books only a line marked with its code. An acquisition whose collected side D406 reports with it (`d406CollectedWithAcquisition`: reverse charges, intra-community acquisitions) also books that side's 4427 line. A cash-VAT release (3801xx) books its 4426 or 4427 line and takes the same base and VAT back from 4428 (a `deferred` side with negated amounts); its direction is its line's, or the transaction's when exactly one of 4426 and 4427 is present (`TAX_DIRECTION_UNKNOWN` otherwise). A marker on a VAT line that no operation of the transaction claims books that line alone, with a zero base and tax. A sole entry on a line books the line's amount, several entries their own amounts; input VAT deducts what it books and output VAT nothing, so the paired 30xxxx/35xxxx blocks of a non-deductible purchase are one acquisition: the operation books the 4426 debit with its base and VAT, the 35xxxx marker books the reversing 4426 credit with a zero base and tax, and the VAT and its base count once with nothing deducted. Deductible and non-deductible operations whose readings pair as `readD406` pairs them split their acquisition when, on one line, their bases add up to the line and neither is the whole line, or, on two lines, each base is its own line; otherwise `readD406` decides overlap or split from the rate's VAT, which the driver does not compute, and the transaction is refused (`TAX_PAIR_UNDECIDED`). An operation without a base reads its line's amount as `readD406` reads invoice lines; on a VAT line that amount is the VAT itself, so it is refused (`TAX_BASE_MISSING`). Entries carry the reading's semantic code and the attributes `saftTaxType`, `saftTaxCode`, `role` (`operation`, `collected`, `deferred` or `marker`), `sourceLine` and `sourceBlock`. Their VAT period is the transaction's month, which is the engine's own period for a company without a `vat.period` fact; an entry on 4428 is not exigible and keeps its operation's period, as the engine's invoice treatment does, while a marker on 4428 has none. A VAT line left without entries is left to the engine, which refuses it.

A transaction the translation or the engine refuses (a blocked proposal, with its blocking codes joined by `+`, or an error at proposal, approval or posting, with its code and any database invariant) is recorded once and never retried; the next transaction follows. After each interval the driver compares the engine's balances with the filing's (`compareBalances` with `zeroPresence: 'separate'`, plus `checkSourceChain` from the previous kept interval) and the engine's journal with the filed transactions (`compareJournals`, the opening left out). The filed side of the tax comparison keeps operations and other taxes, with supplements stating each operation's deductible amount and VAT period as posted; the engine side keeps the `operation` entries under their filed code. Differences are reconciled in the scopes `balances:<interval>`, `journals:<interval>` and `replay:<interval>` (settlements and an opening refusal).

The driver classifies what it knows the cause of, through `context.cause`: a refused transaction's `journal-only-source` as `unsupported` (`mapping` for a mapping refusal), with the refusal in its context; source-chain and other filed-file findings, a reused invoice key and an account's later balances after a break in the filed chain as `source-inconsistency`; zero presence as `comparator`; an off-balance account's balances and a journal tax difference over a non-VAT tax as `unsupported`; a journal tax difference over a baseless marker as `missing-evidence`; and balance and journal-line findings resting on an assumption about an account's mapping as `mapping`. A placeholder's acceptance is recorded on the balance differences of the account bound to it and on the journal differences of the transactions that used it, without classifying them. The translation's notes are recorded in `context.notes`. Balances of an account a refused transaction touched stay unclassified: the summary's `refusalsAndBalances` names, for each refusal reason, the synthetic accounts its transactions touched and those whose balances diverged then or later; `divergedAfterFiledChainBreak` and `divergedOtherwise` list the rest.

The summary carries counts and synthetic account codes only: periods kept, collapsed and balanced, and per period its transactions, postings, refusals and differences; mapping blockers and waived problems by code; lab assumptions by kind and their use; setup counts; the opening; refusals by stage and code; acknowledged warnings; items, settlements by document, unallocated settlements by reason, reused invoice keys and attached import markers; the refusal attribution; and open differences by class and kind. It has no names, fiscal codes, personal codes, document numbers or amounts. The manifest is private: the kept filings' hashes and evidence, the collapsed re-filings and the assumptions applied.
