# Security and trust boundaries

## Assets and authority

Protect company records/evidence, identities/memberships, ANAF and provider credentials, signing permissions, release keys, audit history and backups. Treat owners, accountants, jobs, documents, provider outputs and integration callbacks as distinct principals or untrusted inputs.

Host administrators can ultimately alter their own infrastructure; append-only application records do not prove immunity to a fully compromised host. Signed releases, retained manifests, restricted operations and independent backups provide detection/recovery evidence. Do not promise impossible tamper-proof self-hosting.

## Threat model

| Threat | Required controls and verification |
|---|---|
| Cross-company exposure or IDOR | Company-scoped commands and typed queries, company-consistent foreign keys, object/export/job isolation, membership checks before replay/execution and adversarial authorization tests. SQLite/Turso credentials stay in trusted backend processes. |
| Malicious/compromised accountant | Least-privilege roles, explicit mandates, exact-version approvals, no evidence rewriting, recorded corrections, revocation and anomalous-activity audit. |
| Prompt injection or compromised AI output | Documents are data; typed/schema-validated proposals; deterministic source authority/commands; no raw SQL, credential access or arbitrary tool execution. What an agent extracts from a PDF or a photo is recorded as `extracted`, with each field's citation checked against the file's text layer and the document's arithmetic checked by the engine; every proposal reading it needs a person's acknowledgement (`SOURCE_EXTRACTED`), a policy posts it only if it names that code, and an e-Factura copy of the same invoice outranks it (`BETTER_SOURCE`). A transcribed bank statement whose citations do not hold is refused; one whose citations no text layer verified (a scan, a photo) is, for posting policies, an extracted source: its movements are posted automatically only where a `sourceAuthority` condition allows `extracted`, in the application and in the database (`inv:binding`). |
| Malicious PDF/image/XML, XXE or expansion bombs | Isolated parsers/converters, disabled external entities/network fetches, resource/time/page/dimension limits, quarantine and fuzz tests. Implemented PDF text reader (`evidence.read`, `adapters/pdf-text.ts`): pdf.js in a separate Bun process per file, at most two at a time; 20 MiB in, 200 pages, 2 MiB of text, 512 MiB resident (a watchdog thread kills the process: decompression bombs), 10 s wall time (the process is killed). The process gets the PDF on stdin and an empty environment (no secrets), loads no `.env`, auto-installs nothing, cannot load native addons, and has no `fetch`, WebSocket or WebAssembly; pdf.js gets no font/CMap/wasm URL, loads no fonts and runs its worker on the same thread (pdf.js 6 has no eval path). Every outcome is typed (`encrypted`, `corrupt`, `too_large`, `timeout`, `failed`) and never crashes the API; tests cover corrupt, encrypted, 201-page, text-limit, decompression-bomb, deeply nested and timed-out PDFs. Images get no server-side decoding or OCR: `evidence.read` in `image` mode judges the format from the leading bytes (JPEG, PNG, GIF, WebP; HEIC, AVIF, TIFF and BMP refused) and reads the dimensions from the header alone, refusing a side over 8000 px and a file over 3.75 MiB (5 MiB of base64). CSV bank exports are parsed in-process (`xfactura-core/src/bank/csv.ts`): 2 MB, 2000 movements, a declared encoding with undefined bytes refused, unterminated quotes refused. Not yet: an OS sandbox (network namespace, seccomp) around the reader, which runs with the API's user and filesystem access. |
| ZIP bombs/path traversal | Implemented archive import: central-directory/lazy stream reader, 10 MiB compressed/per-file, 40 MiB expanded, 100 entries and 200:1 expansion; actual sizes/CRC checked. No path extraction to disk. Reject unsafe/duplicate paths, links, special/encrypted/nested files and unsupported methods. Every XML member shares UTF-8/DTD/complexity controls. Original archive/member bytes and immutable provenance survive failed-batch retries and restore. Signatures remain unverified evidence. |
| CSV formula injection and hostile Unicode | Safe spreadsheet exports, text escaping without modifying stored evidence, encoding tests and displayed identifier checks. |
| SSRF and data exfiltration | Provider endpoint allowlists, restricted egress, no document-chosen URLs, private-network protections and verified redirects/downloads. |
| Stolen ANAF/provider/bank credentials | Encryption with separately protected keys, masked UI/logs/exports, rotation/revocation, scoped access and audited use; live bank credentials are outside initial scope. |
| Forged/replayed callbacks and external-action retries | Signed/authenticated integrations, replay protection, idempotency, durable attempts and explicit uncertain-result state. |
| Dependency/release compromise | Pinned lockfiles/images, provenance/SBOM/license review, signed fiscal/software manifests and isolated update/release credentials. |
| Backup compromise or restore drift | Encrypted off-site copies, restricted deletion/access, key recovery, retention policy, restore drills and reconciliation of pending external attempts. |

Implement concrete limits and negative cases before enabling each parser/integration; a future cloud/provider switch cannot bypass them. Default self-host file storage must reject traversal and use atomic immutable writes within the configured volume.

## Delegated accounting access

The implemented agent grants are company-scoped, expiring and revocable; their authority also depends on the delegating human's current membership and role. Grants cannot contain approval, membership-management or credential-management capabilities. The database backs this: approvals, action decisions and posting policies record the agent that made them, and refuse one (`inv:approval_person`, `inv:decision_person`, `inv:policy_person`). Keep API credentials separate from Piatra/OpenAI/OpenRouter inference credentials. Store only token hashes; retain agent/delegator attribution without placing bearer credentials in audit events, command results or ordinary exports. Identical issuance retries can recover the credential through installation-secret derivation, but cannot revive expired/revoked authority.

Recheck grants before cached command responses, source/export downloads and queued export processing/completion. Agent keys have separate idempotency namespaces from human commands. Exact action reviews preserve input/effect hashes, approval and execution lineage under database guards; changed accounting state blocks execution. Tests cover direct legacy-route bypasses, forbidden self-approval, role downgrade, revocation, tenant boundaries and restore/retry behavior.

MCP accepts explicit accounting bearer credentials and requires authentication on every request. Browser cookies cannot authenticate MCP; invalid bearer headers cannot fall back to a browser session. Browser OAuth delegation is not yet implemented. Host validation admits the public hostname, local loopback for local installs and explicitly configured internal proxy hosts. A supplied Origin must match the public origin; session-cookie mutations still require it. Never use arbitrary forwarded headers to extend that allowlist. Request bodies over REST and MCP are bounded to 70 MiB, stored originals to 64 MiB, and inline MCP source reads to 256 KiB: agents read evidence only through `evidence.read`, whose every text result is at most its `maxBytes` (≤ 256 KiB); the whole file (`evidence.get`, the REST download) is for people only, and no grant can name it. The one exception is an image (`evidence.read`, mode `image`): a JPEG, PNG, GIF or WebP of at most 3.75 MiB, so at most 5 MiB of base64, the per-image limit of the common vision models, sent to an agent's own model because the engine does no OCR; over MCP it travels once, as an image content block. A PDF, or any file that is not such an image, never leaves whole.

## Personal data

CNPs, health data (who was on sick leave, the certificates' indemnity and diagnosis codes, work accidents) and individual pay are personal data. The engine never prints or logs one; an error that might quote a CNP (ANAF's PDF tool) is masked before it is raised.

- **At rest.** CNPs and diagnosis codes are sealed (AES-256-GCM under a key derived from the installation's secret, bound to the company) and opened only into the files that must carry them: a return's XML, a B2C invoice's (BT-47). A party's identifier for an individual is never the CNP or an unkeyed hash of it (a birth date leaves a few thousand candidates): it is an HMAC of the CNP's SHA-256 under a per-company key derived from the same secret (`cnp:k1:…`, `db/identity.ts`), deterministic so that an employee who buys from the company is one party. The database refuses any other identifier for an individual (`inv:party_identity`), and any Romanian partner of whatever kind known by 13 digits (`inv:party_cnp`, 5 November 2026: a received e-Factura invoice of an individual recorded its seller as a company under the CNP in clear; it now records the individual). Migration 0031's data step rekeys the earlier `cnp:<sha256>` identifiers, a CNP kept as an individual's identifier, and a partner of another kind known by a CNP (it becomes the individual; a copy of an individual already known keeps no identifier), under the secret the migration is run with (`bun run db:migrate` reads `ACCOUNTING_AUTH_SECRET`); a database holding them refuses to migrate without it. A month's sick leave is sealed the same way (6 November 2026): each medical certificate a payroll run paid is kept sealed whole (series and number, indemnity code, dates, the codes D112 asks, the diagnosis and a cared-for person's CNP sealed within), opened only by the next month's computation, which continues its episode, and by the D112 writer; a run's issues about a certificate keep their mark without their code and message, opened for a reader of health data; its sick items are labelled without the certificate; and an answer about a month's absences keeps each absence sealed but for its certificate's file, which classification and the worklist read, opened for a reader of health data. The database refuses them in clear (`inv:sick_sealed`, `inv:absence_sealed`), and migration 0032's data step seals what earlier runs and answers kept, under the secret the migration is run with. The sick items' kinds (`sick_fund`, `accident_employer`, `sick_fund_exempt`, …) stay in clear: they decide the contributions' bases and the tax, and D112's sums, on every computation, protected by the access rules below. A command's stored result for replay is the command's own; what a caller reads of it is decided each time it is returned (below).
- **Who reads health data.** Owners and reviewers, as for CNPs and pay: the employer receives each medical certificate, which bears its codes, and pays the sick leave; the accountant, a reviewer, files D112, whose section D declares each certificate's diagnosis (the threat model above keeps the accountant to a least-privilege role and an explicit mandate; a member's role is the mandate). A viewer, who records neither, never does. An agent does only when its grant names an operation that declares `health` (`payroll.absences.list`, or an export, which holds everything); no toolset expands to one, so no grant issued before gains it: expansions are stored when a grant is issued, and none held such an operation (a grant naming `exports.get` already downloaded every file).
- **Files.** A file's data classes come from the records that use it: a return's files (`tax`; `personal` for the returns carrying CNPs; D112 also `payroll` and `health`, by kind, so that a file's classes never tell that someone was ill), a file a document reads whose counterparty is an individual known by a CNP, a file a payroll record cites (a run's benefit documents included; a run prepared before 5 November 2026 did not name them, so every file nothing in the books uses, recorded by the latest such run, is taken for one, `payroll` and `personal`, and the worklist lists it as unused without its name), the answer to a question about the month's benefits (`payroll`, `personal`) or sick leave (and `health`) and every file it cites (the medical certificates), a family enterprise's agreement. `evidence.read`, `evidence.get` and the REST download refuse a file whose classes the caller may not read, saying which and whether its grant or its role stops it (`EVIDENCE_CLASS`, `details.missing`, `details.reason`); `evidence.list` lists it without its name, and no citation is checked against it for that caller, since a citation's outcome would tell what the file holds. An agent's own extraction becomes `personal` once the document it recorded names an individual by CNP: it reads it again only if its grant covers `personal`.
- **Views.** Every view that leaves the engine is redacted for its caller, the views a write returns included (`.propose`, `.revise`, `proposals.*`, `ledger.post`, `*.request`, `actions.*`, `questions.*`, `payroll.runs.prepare`), on the first return and on every retry. For a caller who may not read personal data, CNPs are masked in documents (body and citations), proposals' effects and issues, action previews, returns' steps (ANAF's validator may quote a record), the margin scheme's register, ANAF's messages and the worklist; an individual's details (address, contact) are withheld; agents see individuals' party identifiers masked (`parties.*`, `vat.journal`). A caller who may not read pay (an agent whose reads do not cover `payroll` and `personal`, or a viewer, 6 November 2026) sees the personnel accounts (class 42) summed without the person in proposals' effects, the journal, the year close's preview and the opening's differences, and none of their open items or partner lines (`openItems.list`, the inventory registers). A payment of pay (money on 512x or 531x against 421, 423, 425 or 426; a movement nobody explained yet whose counterparty is an employee, by name or by an account pay already went to) is `Plată salarii` to such a caller: no name, IBAN, reference, description or memo, and its amount only when it pays two people or more (a salaries batch's total); one person's is withheld. It is so per movement in `bank.movements` and the worklist's `bank.unexplained`, per entry in `ledger.journal` and `pfa.journal`, per member in a batch's preview and per posting in `templates.performance` (`agents.performance` and a template request's backtest too); the cash register, whose balances state each day's total anyway, shows a day's payments of pay as one row with their total. A proposal paying pay is withheld whole (effect and input null, its issues saying only that they concern salaries); an agent that may not read pay is refused proposing one (`PAY_DATA`, with the classes missing), and the worklist's steps it may not take name what stops it (`needs`), so that the item waits on a person. The year-end's confirmations of personnel balances (an advance on 425) are one item per account and currency, whose id names no one: who and how much only for a reader of pay (`yearend.review`, its worklist items, `inventory.compare`); the year close's findings name no one to anyone. For a caller who may not read health data, answers about sick leave (questions, a proposal's basis, `payroll.absences.list`) keep their place without their value, a payroll run's certificate issues and D112's problems about a certificate name no one, and a D112's steps carry no detail from ANAF. Every D112 tells such a caller when it is due, never why (6 November 2026): a quarterly employer's month brought forward by sick leave or a contract that ended (art. 147 alin. (11)) would be told by the summary's basis and by the deadline's rule, so every D112's summary names the return's deadline alone (`deadline: D112`, no `counted`, `basis` or `event`), and so do the calendar (no parameter versions or readings), `closure.evaluate` and the worklist, whatever the basis, so that the redaction itself tells nothing. In a payroll of one person the sick pay the fund bears (4382) is that person's and says they were ill: such a caller reads it folded into 641 (`includes: ['4382']`, whether or not there was sick pay) in the proposal's effect and the journal; a payroll of two people or more shows it as booked. The change feed names records, never content. [AGENT_API.md](AGENT_API.md#personal-data) has the details.
- **Exports** hold everything. Requesting one needs review permission, is irreversible (`high` risk) and declares every class but credentials, health included, so no toolset grants it; its status and download are for its requester alone (an agent: the same grant) or an owner, and anyone else is told it does not exist.

Not yet (6 November 2026):
- registers that state totals stand as booked, and a withheld amount may be recomputed from them: the trial balance and the general ledger (a month's 4382 in a company of one employee, a payment of pay against the month's turnover), a statement's balances, a batch's totals per account, the cash register's day balances; a payroll of one person shows that person's pay summed (421 per side) to a caller who may not read pay;
- a viewer reads each employee's pay in `payroll.runs.get`, `.list` and `payroll.contracts.list`, people's operations whose permission is `read`; the books' views withhold it;
- a payment of pay to an account nobody's pay went to yet, under a name that is not the employee's, reads as any payment until it is explained;
- an inventory list (`documents.get`) names the people whose confirmations it records;
- results of commands recorded before 6 November 2026 keep the sick leave they returned in `acc_commands` (the audit chain binds their hashes), read only through the views' redaction; an answer's own file and the medical certificates are evidence kept as recorded, read only under the class rules above.

## AI evidence egress

Before transmission, disclose the provider and company-approved purpose. Record evidence identifiers/hashes, provider/model, time, actor, policy/action, and selected retention/privacy configuration. Do not claim a provider enforces a retention mode unless its account/API contract supports it.

Keep raw prompts and credentials out of ordinary logs. Store only the evidence/proposal/audit material needed for reconstruction under its retention class. Enabling a model does not grant it access to unrelated companies or the full document store.

## Disclosure, retention and gates

Before the public pilot, publish a monitored private vulnerability intake, responsible maintainers, response process and advisory route. Enable repository private reporting where supported; do not invent an unmonitored security address.

Classify source documents, accounting/fiscal records, identity data, usage and integration logs separately. Verify period-specific retention/erasure requirements with the fiscal/source register; avoid copying old retention figures from a single unreviewed source.

Security release gates include tenant/portfolio isolation, distinct professional/product/submission authority, permission revocation during queued work, exact signed-payload/receipt linkage, malicious parser inputs, export safety, credential recovery, supply-chain checks and clean-room restoration.
